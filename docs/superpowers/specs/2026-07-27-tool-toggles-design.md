# Tool On/Off Switches — Design

**Date:** 2026-07-27
**Status:** Approved, ready for implementation planning

## Summary

Give each of MiniMe's user-facing tools an on/off switch in Settings. Turning a
tool off makes it disappear: its item leaves the menu bar menu, its global
hotkey is unregistered, and its Settings tab and Shortcuts row are hidden. Any
state the tool was holding is torn down.

The switches live together in a single `Tools` section in the General tab, so
one screen shows what is on and what is off.

## Goals

- One place to see and change which tools are active.
- A disabled tool is genuinely inert — no menu item, no working hotkey, no
  orphaned settings UI, no background work.
- Existing installs keep every tool on; nobody loses a feature by upgrading.
- Adding a sixth tool later means adding one enum case, not editing five files.

## Non-goals

- Disabling the Scheduler. It has no menu-bar presence and is inert until
  explicitly armed, so a switch would add UI without removing anything.
- Per-tool permission management (Screen Recording, Accessibility).
- Hiding the General, Scheduler, Shortcuts, or About tabs.
- Reordering menu items or tabs.

---

## 1. The `Tool` model

New file `MiniMe/Models/Tool.swift`:

```swift
enum Tool: String, CaseIterable, Identifiable, Sendable {
    case capture
    case typeIt
    case clipboard
    case moveMouse
    case preventSleep

    var id: String { rawValue }
    var title: String       // "Capture", "Type It", "Clipboard", …
    var icon: String        // SF Symbol shown in the Tools row
    var defaultsKey: String // "tool.<rawValue>.enabled"
}
```

`Tool` is the single source of truth. The Tools section, the menu-bar items, the
Settings tab filter, the Shortcuts sections, and hotkey registration all derive
from it.

The Scheduler is deliberately not a case.

`preventSleep` is a case even though it has no hotkey and no dedicated tab —
disabling it removes its menu submenu, which is the point.

## 2. Persistence

`SettingsManager` gains:

```swift
@Published private(set) var enabledTools: Set<Tool>

func isEnabled(_ tool: Tool) -> Bool
func setEnabled(_ tool: Tool, _ enabled: Bool)
```

`enabledTools` is loaded in `init` from `UserDefaults`. **An absent key means
enabled**, so existing installs and fresh installs both start with every tool
on. `setEnabled` writes the key and updates the published set; teardown is
split between `SettingsManager` and the app layer as described in §6.

### Migration

`clipboardHistoryEnabled` is being removed (§3). On first launch after the
upgrade, if that key exists and is `false`, `Tool.clipboard` starts disabled;
the old key is then deleted. A user who had clipboard history switched off does
not get it silently switched back on.

## 3. Settings UI

### General tab

A new `Tools` section, below `App`:

```
┌─ Tools ───────────────────────────┐
│ ◎ Capture                  [ on ] │
│ ⌨ Type It                  [ on ] │
│ ⎘ Clipboard                [ on ] │
│ ↺ Move Mouse               [off ] │
│ ☾ Prevent Sleep            [ on ] │
│ Turning a tool off hides it from  │
│ the menu bar and disables its     │
│ shortcut.                         │
└───────────────────────────────────┘
```

Rows are generated by iterating `Tool.allCases`, using the existing
`SettingsRowIcon` + `Toggle` layout the other sections use.

The `System` section and its `Prevent sleep` toggle are **deleted**. That toggle
armed the feature; arming stays where users already do it, in the menu bar
submenu. Keeping both would put two similar-sounding Prevent Sleep controls on
the same screen meaning different things.

### Tab bar

`SettingsView` currently hardcodes eight `SettingsTabButton`s and tracks
`selectedTab` as an `Int` compared against literals (`selectedTab == 4`). That
breaks as soon as a tab can disappear — indices shift.

The tab bar becomes a data-driven list:

```swift
private struct SettingsTab: Identifiable {
    let id: String
    let title: String
    let icon: String
    let gradient: LinearGradient
    let requires: Tool?   // nil = always shown
}
```

Selection is held as `id: String`, not an index. The content `switch` keys off
the same id. Tabs whose `requires` tool is disabled are filtered out. General,
Scheduler, Shortcuts, and About have `requires == nil` and are always present.

If the currently selected tab is filtered away while Settings is open,
selection falls back to General.

### Clipboard tab

The `Enable clipboard history` row is removed. The `Tools` switch now starts and
stops the monitor. The rest of the tab (retention limit, pick behavior, capture
options, clear history) is unchanged.

### Shortcuts tab

Each `Section` is rendered only when its tool is enabled, so the tab lists only
shortcuts that actually fire. `Reset to Defaults` is always shown and continues
to reset all four shortcuts regardless of enablement — it resets stored values,
not availability.

## 4. Menu bar

In `MenuContentView`, each tool's button is wrapped in a check against
`settings.enabledTools`. Dividers are emitted conditionally so a disabled tool
never leaves a leading, trailing, or doubled separator.

`Settings…` and `Quit` are never filtered.

`AppDelegate.showPopupMenu()` builds a second, native `NSMenu` as a fallback
when the status item button can't be found. It must get the same filtering —
it is easy to overlook and would otherwise show disabled tools.

## 5. Hotkeys

`ShortcutSet` gains `var enabledTools: Set<Tool>`, populated by
`SettingsManager.shortcutSet`. `HotkeyManager.startMonitoring()` registers a
shortcut only when its tool is in the set.

`ShortcutSet` is already `Equatable`, and `MiniMeApp` already has:

```swift
.onChange(of: settingsManager.shortcutSet) { _, newValue in
    hotkeyManager.updateShortcuts(newValue)
}
```

Adding `enabledTools` to the struct means flipping a switch changes the
`ShortcutSet`, which fires that existing observer, which re-registers hotkeys.
No new observation code.

The Escape hotkey used during selection is separate and unaffected.

## 6. Side effects on disable

Disabling a tool tears down whatever it was holding. Teardown is split by
ownership: `SettingsManager` handles only what it can reach, and the app layer
handles the objects `MiniMeApp` owns.

| Tool | Teardown | Runs in |
|---|---|---|
| Capture | `screenCapture.cancelAreaSelection()` | App layer |
| Type It | None — no persistent state | — |
| Clipboard | `monitor.stop()` and `panel.close()` | App layer |
| Move Mouse | `MouseMoverManager.shared.disarm()` | App layer |
| Prevent Sleep | `disablePreventSleep()` — releases the IOKit assertion | `SettingsManager` (owns the assertion) |

Move Mouse moved to the app layer during implementation. Reaching
`MouseMoverManager.shared` from `SettingsManager` would have made the teardown
testable only by arming the real mover, which needs Accessibility permission
and schedules an actual cursor move — a test that either moves the user's
mouse or passes vacuously when permission is denied. Keeping all cross-object
teardown in one place leaves `SettingsManager` owning only the assertion it
actually holds, which is testable against real IOKit.

`ClipboardMonitor`, `ClipboardPanelController`, and `ScreenCaptureManager` are
owned by `MiniMeApp`, not by `SettingsManager`. Their teardown hangs off a
`.onChange(of: settingsManager.enabledTools)` observer in `MiniMeApp`, replacing
the existing `.onChange(of: settingsManager.clipboardHistoryEnabled)` observer,
which is removed along with that setting. This follows the wiring pattern
already used for the other clipboard settings.

Prevent Sleep matters most: leaving the assertion held while removing the only
UI to release it would keep the Mac awake indefinitely with no way to stop it.

Re-enabling Clipboard restarts the monitor. Nothing else auto-re-arms — Move
Mouse and Prevent Sleep return to their idle state and wait to be started.

Because `MouseMoverManager`, `ScheduledActionManager`, and `TypingService`
drive the menu-bar icon glyph, disarming on disable also restores the icon.

## 7. Edge cases

**The menu-bar-icon hint.** General's `Show menu bar icon` row currently shows
*"Use your capture hotkey to interact with MiniMe."* when the icon is hidden.
With Capture disabled that instruction is false, and hiding the icon while
Capture is off leaves the app reachable only by relaunching it. The hint is
reworded to name an enabled tool's shortcut, and to warn when no enabled tool
has one.

**All tools off.** Permitted. The menu becomes `Settings…` and `Quit`. Settings
still shows General, Scheduler, Shortcuts, and About, so everything is
recoverable.

**Settings open while toggling.** Disabling a tool hides its tab immediately;
selection falls back to General if that tab was showing.

## 8. Testing

New tests in `MiniMeTests/`, using Swift Testing (`@Test`), consistent with the
existing suites:

- `ToolTests` — `defaultsKey` stability per case; absent key reads as enabled;
  persistence round-trips through `UserDefaults`.
- Migration — `clipboardHistoryEnabled == false` yields `Tool.clipboard`
  disabled and clears the legacy key; `true` or absent yields enabled.
- `ShortcutSetTests` — two sets differing only in `enabledTools` are unequal.
  This is what makes hotkey re-registration fire, so it is worth pinning.
- `SettingsManagerTests` — disabling each stateful tool triggers its teardown;
  re-enabling Clipboard restarts the monitor and re-enabling the others does
  not auto-arm.

View-level filtering can't be reached from unit tests, so `ToolToggleUITests`
drives the real app for it. MiniMe is an accessory app with no ordinary window,
so `⌘,` does nothing until the status item menu is open — the tests click the
status item, then `Settings...`, the way a user does. They cover: the Tools
section rendering all five switches; switching Clipboard off removing it from
the menu bar menu and switching it back on restoring it; a disabled tool's
Settings tab disappearing; and a disabled tool's Shortcuts row disappearing.

Each Tools toggle carries an `accessibilityIdentifier` of
`tool-toggle-<rawValue>`, because SwiftUI renders a `Form` toggle as a `Switch`
whose label is a sibling `StaticText` — there is no title on the control to
match against.

These tests run against the user's real preferences (the app uses
`UserDefaults.standard`), so each one restores what it flipped.

Note: the pre-existing `SettingsUITests` are written as
`if element.exists { XCTAssert(element.exists) }` behind a
`guard ... else { return }` on a Settings window that never opens, so they pass
unconditionally without asserting anything. They were left as-is — fixing them
is unrelated to this change — but they should not be read as coverage.
